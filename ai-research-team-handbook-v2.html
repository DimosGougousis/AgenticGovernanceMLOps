Architecture templates, orchestration patterns, and tool-specific implementation guides for production-grade multi-agent research systems — using LangGraph, Langflow, n8n, LangSmith, and AWS.

1. Agentic Architecture Primer

An agentic system is a software system where a language model controls the flow of execution — choosing tools, invoking sub-agents, and updating shared state until a goal is satisfied or an escalation condition is met. The key architectural shift over "God Prompt" systems is that complexity moves from the prompt into the graph: explicit nodes, typed state, defined transitions, and deterministic control over irreversible actions.

1.1 Anatomy of an Agent

Every agent in a production system has five components. Designing each explicitly prevents the most common failure modes.

ComponentWhat it isProduction requirement
System prompt The agent's role, scope, output format, and constraints. Version-controlled in Git; pinned at deployment; includes explicit scope limits (what the agent must NOT do).
Tools Typed functions the agent can call: search, DB read/write, API call, code execution. Least-privilege — read tools and write tools are separate objects. Each tool has a JSON schema the framework validates before execution.
Memory In-context state, external vector/graph store, or episodic log. Three layers: in-context (current task), semantic (vector DB for retrieval), episodic (structured log via Zep or Mem0).
Control flow The logic that decides when the agent stops, loops, or hands off. Explicit exit conditions; max-iteration guards; typed output schemas so downstream nodes parse reliably.
Observability Traces, metrics, and logs emitted by the agent at runtime. OpenTelemetry spans per tool call; cost and latency captured per node; trace IDs propagated across agent handoffs.

2. The 4-Agent Research Squad — Templates

A production research desk decomposes into four cooperating agents. Each has a single responsibility, typed inputs/outputs, and tool access scoped to its mission.

🧠
Planner
Converts ambiguous user requests into a structured DAG of tasks with explicit dependencies, success criteria, and HITL gates.
Claude Opus 4 / GPT-4o
🔍
Retriever
Pulls ranked evidence from vector stores, graph DBs, SQL, and APIs. Returns citations in a canonical structured format.
Claude Haiku / GPT-4o-mini
⚔️
Critic
Adversarial reviewer — checks evidence and drafts for gaps, contradictions, missing citations, and policy violations.
Claude Sonnet / GPT-4o
✍️
Writer
Evidence-bound synthesizer. Forbidden from free-form research — receives only critic-approved artifacts and writes structured output.
Claude Sonnet / GPT-4o

2.1 Planner — Template

The Planner is the only agent with full access to the user query. It emits a machine-readable plan — not prose — so all downstream agents parse it deterministically.

System Prompt Template

# PLANNER SYSTEM PROMPT
You are a research planning agent. Your only job is to decompose
the user request into a JSON task DAG. Do NOT perform research.

Output schema (TypeScript):
interface Plan {
  goal: "string";                  // restated goal, one sentence
  tasks: Task[];
  hitl_checkpoints: "task_id"[]; // tasks requiring human approval
  success_criteria: "string"[];   // measurable exit conditions
  abort_conditions: "string"[];   // conditions triggering stop
}

interface Task {
  id: "string";         // e.g. "T1", "T2"
  role: "retriever" | "critic" | "writer" | "human";
  description: "string";
  depends_on: "task_id"[];
  parallel: boolean;   // can run alongside sibling tasks?
  tools: "string"[];    // from approved tool registry
  max_retries: number;  // loop guard
}

Rules:
- Favor small tasks with a single clear output.
- Mark parallel: true only when tasks have no data dependency.
- Never assign tools outside the approved registry below.
- Insert hitl_checkpoints before any external publish or write action.

Approved tool registry: web_search, kb_lookup, sql_read, graph_query,
code_run_sandbox, draft_email (read-only tools only at Retriever stage).

Output Example — Plan DAG

2.2 Retriever — Template

The Retriever's output quality is the single biggest lever on the final answer. Measuring retrieval separately from generation — recall and faithfulness as distinct metrics — is the non-negotiable first step.

System Prompt Template

# RETRIEVER SYSTEM PROMPT
You are a retrieval specialist. Execute exactly the task assigned by
the Planner. Return evidence in the canonical citation format below.
Do NOT synthesize, interpret, or write conclusions.

Citation format (required for every snippet):
[SOURCE_ID · source_name · section/lines · retrieved_at · confidence:0-1]

Output schema:
interface RetrievalResult {
  task_id:    "string";
  snippets:   Snippet[];
  coverage:   "complete" | "partial" | "insufficient";
  gaps:       "string"[];  // topics with no evidence found
  corpus_ver: "string";   // version tag for reproducibility
}

interface Snippet {
  text:       "string";
  citation:   "string";  // canonical format above
  confidence: number;    // 0–1 retrieval score
  freshness:  "string";  // ISO date of document
}

Rules:
- If coverage is "insufficient", surface gaps immediately — do not invent.
- Tag documents older than 90 days as STALE in the citation.
- Use graph traversal (not similarity search) for named entities.

Tool Wiring — Retriever Tool Set

2.3 Critic — Template

The Critic is optimized for error detection, not fluency. It outputs a machine-parseable diagnostic that drives the orchestrator's feedback loop.

System Prompt Template

# CRITIC SYSTEM PROMPT
You are an adversarial reviewer. Examine the evidence artifacts below
and return a structured diagnostic. Do NOT rewrite or improve — only detect.

Output schema:
interface CriticReport {
  status:   "NO_GAPS" | "GAPS_FOUND" | "ABORT";
  issues:   Issue[];
  confidence_floor: number; // lowest confidence score across snippets
  retry_tasks: "task_id"[]; // tasks the Retriever must redo
  abort_reason?: "string";   // required if status === "ABORT"
}

interface Issue {
  type:        "missing_citation" | "contradiction" | "stale_source" |
               "policy_violation" | "coverage_gap" | "low_confidence";
  description: "string";
  severity:    "low" | "medium" | "high" | "critical";
  location:    "string"; // snippet ID or task reference
}

Rules:
- Set status ABORT if any issue is "critical" or confidence_floor < 0.4.
- Set status GAPS_FOUND if retry_tasks is non-empty.
- Set status NO_GAPS only when zero issues are detected.
- Maximum 3 GAPS_FOUND cycles before escalating to human review.

2.4 Writer — Template

The Writer receives only critic-approved evidence. Tool access is disabled — it cannot perform additional research. Unsupported claims are a schema validation error.

System Prompt Template

# WRITER SYSTEM PROMPT
You are an evidence-bound technical writer. You will receive a validated
evidence package and a target format. Write ONLY from the evidence provided.

Hard constraints:
- Every factual claim MUST reference a snippet citation by ID.
- If evidence is insufficient for a section, write: [INSUFFICIENT EVIDENCE — flag for human review]
- Do NOT use training knowledge. Evidence package is the only source.
- Tool access: NONE.

Output schema (varies by format — example: report):
interface Report {
  title:            "string";
  executive_summary: "string";  // ≤150 words
  sections:          Section[];
  citations:         Citation[];  // full citation list
  confidence_score:  number;       // avg of all snippet confidences used
  review_flags:      "string"[];  // list of sections needing human review
}

2.5 Shared State Schema

All agents read from and write to a single typed state object managed by the orchestrator. This prevents implicit coupling and makes every transition auditable.

# Shared State — TypeScript interface (maps to LangGraph StateGraph annotations)
interface ResearchState {
  // Core identifiers
  run_id:         "string";          // UUID; propagated as OTel trace ID
  user_query:     "string";
  plan:           Plan | null;

  // Retrieval
  evidence:       RetrievalResult[];
  retrieval_iter: number;           // incremented each Retriever call

  // Critique
  critic_report:  CriticReport | null;
  critic_loops:   number;           // guard against infinite loops

  // Output
  draft:          Report | null;
  final_output:   Report | null;

  // Control
  hitl_pending:   boolean;
  hitl_decision:  "approved" | "rejected" | null;
  status:         "planning" | "retrieving" | "critiquing" | "writing" |
                  "hitl_wait" | "complete" | "aborted";
  error:          "string | null";
}

3. Orchestration Pattern Templates

The same four agents produce different systems depending on how they are wired together. Choose the simplest pattern that satisfies your reliability and latency requirements, then add complexity only where needed.

3.1 Sequential Pipeline

When: fixed, repeatable workflows with compliance requirements (compliance checks, onboarding, weekly reports). Each step has a contract: one input, one typed output, one responsibility.

[ PLANNER ] ──▶ [ RETRIEVER ] ──▶ [ CRITIC ] ──▶ [ HITL? ] ──▶ [ WRITER ] ──▶ [ OUTPUT ] Each arrow = a typed state transition. No branching. No loops. Audit trail: linear, one entry per node, trivially reconstructable. Failure mode: brittle at exception paths — add explicit error nodes, not try/catch.

LangGraph Skeleton

from langgraph.graph import StateGraph, END

graph = StateGraph(ResearchState)
graph.add_node("planner",   planner_node)
graph.add_node("retriever", retriever_node)
graph.add_node("critic",    critic_node)
graph.add_node("hitl",      hitl_interrupt_node)
graph.add_node("writer",    writer_node)

graph.set_entry_point("planner")
graph.add_edge("planner",   "retriever")
graph.add_edge("retriever", "critic")
graph.add_edge("critic",    "hitl")
graph.add_edge("hitl",      "writer")
graph.add_edge("writer",    END)

app = graph.compile(checkpointer=postgres_saver) # durable state

3.2 Concurrent Fan-Out

When: multiple independent data sources or sub-questions; wall-clock latency matters. Fan out Retrievers in parallel, then aggregate.

┌──▶ [ RETRIEVER: web ] ──┐ │ │ [ PLANNER ] ──▶ [ ROUTER ] ──▶ [ RETRIEVER: KB ] ──▶ [ AGGREGATOR ] ──▶ [ CRITIC ] │ │ └──▶ [ RETRIEVER: SQL ] ──┘ Aggregator deduplicates and reranks before passing to Critic. Risk: inconsistent assumptions between parallel workers — aggregator must normalize citations.

LangGraph Fan-Out with Send API

from langgraph.types import Send

def route_to_retrievers(state: ResearchState):
    # Dispatch one Send per parallel task in the plan
    return [
        Send("retriever", {"task": task, "run_id": state.run_id})
        for task in state.plan.tasks
        if task.role == "retriever" and task.parallel
    ]

graph.add_conditional_edges("planner", route_to_retrievers, ["retriever"])
graph.add_node("aggregator", aggregator_node)  # collects all retriever outputs
graph.add_edge("retriever", "aggregator")
graph.add_edge("aggregator", "critic")

3.3 Feedback Loop (Critic → Retriever Cycle)

When: high-stakes outputs, legal/compliance review, accuracy-critical research. The Critic triggers Retriever re-runs until quality thresholds pass. A hard max-loop guard is mandatory.

[ PLANNER ] ──▶ [ RETRIEVER ] ──▶ [ CRITIC ] ▲ │ │ GAPS_FOUND │ status = GAPS_FOUND AND loops < 3 └───────────────┘ │ NO_GAPS ──────▶ [ HITL GATE ] ──▶ [ WRITER ] │ ABORT ────────▶ [ ESCALATE TO HUMAN ] Loop guard: critic_loops ≥ 3 → force ABORT even if GAPS_FOUND. Cost: each cycle adds ~$0.02–0.08 at Haiku rates. Set budget ceiling per run.

LangGraph Conditional Edge — Loop Control

def route_after_critic(state: ResearchState) -> str:
    report = state.critic_report
    if report.status == "NO_GAPS":
        return "hitl"
    if report.status == "ABORT" or state.critic_loops >= 3:
        return "escalate"
    # GAPS_FOUND — increment loop counter, re-run retriever
    state.critic_loops += 1
    state.evidence = []  # clear stale evidence
    return "retriever"

graph.add_conditional_edges(
    "critic",
    route_after_critic,
    {"hitl": "hitl", "retriever": "retriever", "escalate": "escalate"}
)

3.4 Hierarchical Tree (Supervisor → Worker Squads)

When: very large research tasks spanning multiple domains — codebase audits, enterprise intelligence reports, multi-jurisdiction compliance analysis. A top-level Supervisor decomposes into domain-specific sub-teams.

[ SUPERVISOR PLANNER ] / | \ [ SQUAD A ] [ SQUAD B ] [ SQUAD C ] P→R→C→W P→R→C→W P→R→C→W Domain: Legal Domain: Tech Domain: Finance \ | / └──────▶ [ SYNTHESIS WRITER ] ◀──┘ │ [ HITL GATE ] │ [ FINAL OUTPUT ] Risk: information loss through summarization at each level. Mitigation: pass citation IDs (not full text) upward; Synthesis Writer pulls full snippets from shared evidence store by ID.

4. Tool-by-Tool Implementation Templates

The same 4-agent pattern runs in every major tool. The choice is about control, hosting, and team capability — not which architecture to use.

4.1 ◆ LangGraph — Stateful Graph Implementation

LangGraph is the production default for workflows that need durable state, cycles, and deterministic HITL interrupts. Used in production at Uber, JPMorgan, LinkedIn, Klarna (LangGraph v1.0, Oct 2025).

Full Research Squad Graph — Production Template

from langgraph.graph import StateGraph, END
from langgraph.checkpoint.postgres import PostgresSaver
from langgraph.types import Send, interrupt

# ── Node implementations (each wraps a Claude / GPT call) ──────────────
async def planner_node(state: ResearchState) -> dict:
    result = await planner_chain.ainvoke(state.user_query)
    return {"plan": result, "status": "retrieving"}

async def retriever_node(state: ResearchState) -> dict:
    task = state["task"]  # injected via Send
    result = await retriever_chain.ainvoke(task)
    return {"evidence": [result]}  # Annotated reducer appends to list

async def critic_node(state: ResearchState) -> dict:
    report = await critic_chain.ainvoke(state.evidence)
    return {"critic_report": report, "critic_loops": state.critic_loops + 1}

async def hitl_node(state: ResearchState) -> dict:
    decision = interrupt({  # pauses graph; resumes when .update() called
        "critic_report": state.critic_report,
        "evidence_count": len(state.evidence)
    })
    return {"hitl_decision": decision, "hitl_pending": False}

async def writer_node(state: ResearchState) -> dict:
    draft = await writer_chain.ainvoke(state.evidence)
    return {"final_output": draft, "status": "complete"}

# ── Graph assembly ──────────────────────────────────────────────────────
builder = StateGraph(ResearchState)
builder.add_node("planner",   planner_node)
builder.add_node("retriever", retriever_node)
builder.add_node("aggregator",aggregator_node)
builder.add_node("critic",    critic_node)
builder.add_node("hitl",      hitl_node)
builder.add_node("writer",    writer_node)
builder.add_node("escalate",  escalation_node)

builder.set_entry_point("planner")
builder.add_conditional_edges("planner", route_to_retrievers, ["retriever"])
builder.add_edge("retriever",  "aggregator")
builder.add_edge("aggregator", "critic")
builder.add_conditional_edges("critic", route_after_critic,
    {"hitl":"hitl", "retriever":"retriever", "escalate":"escalate"})
builder.add_conditional_edges("hitl", route_after_hitl,
    {"approved":"writer", "rejected":"escalate"})
builder.add_edge("writer", END)

app = builder.compile(
    checkpointer=PostgresSaver.from_conn_string(POSTGRES_URL),
    interrupt_before=["hitl"]   # hard pause before human gate
)

    "criteria",

        "completeness": "Are all success_criteria from the plan addressed?"
    }},

)

    app.invoke,
    data=dataset,

    task = event["task"]
    run_id = event["run_id"]

    # Step 1: Retrieve from Bedrock Knowledge Base
    kb_response = bedrock_agent.retrieve(
        knowledgeBaseId="KB-XXXXXXXXXX",
        retrievalQuery={"text": task["description"]},
        retrievalConfiguration={
            "vectorSearchConfiguration": {
                "numberOfResults": 8,
                "overrideSearchType": "HYBRID"  # semantic + keyword
            }
        }
    )
    snippets = [
        { "text": r["content"]["text"],
          "citation": f"[{r['location']['s3Location']['uri']} · score:{r['score']:.2f}]",
          "confidence": r["score"] }
        for r in kb_response["retrievalResults"]
    ]

    # Step 2: Use Retriever LLM to select/filter relevant snippets
    body = json.dumps({
        "anthropic_version": "bedrock-2023-05-31", "max_tokens": 2048,
        "system": retriever_system_prompt,
        "messages": [{"role": "user", "content":

    response = bedrock_runtime.invoke_model(
        modelId="anthropic.claude-haiku-4-20251001-v1:0",
        body=body, contentType="application/json"
    )
    result = json.loads(response["body"].read())["content"][0]["text"]
    return json.loads(result)  # RetrievalResult schema

5.3 Architecture Quality Checklist

Embed this into your CI pipeline or architecture review template. Every item maps to a known failure mode.

  • State schema is typed and versioned. All agents read/write a single typed state object. Schema is committed to Git alongside the graph.
  • Every tool has a JSON schema. The orchestrator validates tool inputs against the schema before execution. Invalid inputs raise a typed error, not a runtime exception.
  • Read and write tools are separate objects. Retriever agents cannot access write tools. Write tools require explicit approval node preceding them.
  • Feedback loops have hard max-iteration guards. Critic → Retriever loops abort at N iterations (default: 3) and escalate rather than looping forever.
  • HITL gates are hardcoded, not optional. interrupt_before / waitForTaskToken / Wait nodes are in the graph definition, not in the prompt.
  • Prompts are version-controlled and pinned at deploy. LangSmith Hub pull with explicit version tag, or Git SHA reference. No "latest" in production.
  • State checkpoints persist to durable storage. PostgresSaver / DynamoDB / Redis — not in-memory. Long-running runs survive Lambda timeouts and restarts.
  • Eval dataset exists before go-live. Minimum 50 graded scenarios from real or representative inputs, including adversarial cases. Release gate ≥ 85% task completion.
  • Observability records emitted per run. LangSmith trace + CloudWatch metric per run. Escalation rate, cost-per-run, and critic_loops on a live dashboard.
  • Canary deploy with rollback trigger defined. 5% traffic first; pre-committed rollback if task-completion drops below threshold or cost-per-run exceeds ceiling.
  • Model provider failover configured. Priority-ordered fallback: Anthropic → OpenAI → open-weight via Bedrock. Tested and eval-validated before production.
  • Audit trail captures reasoning, not just outputs. Every Critic decision logs the issue list. Every Writer output logs the snippet IDs used. Retained ≥ 90 days.
