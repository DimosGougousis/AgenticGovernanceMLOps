1. Agentic Architecture Primer

An agentic system is a software system where a language model controls the flow of execution — choosing tools, invoking sub-agents, and updating shared state until a goal is satisfied or an escalation condition is met. The key architectural shift over "God Prompt" systems is that complexity moves from the prompt into the graph: explicit nodes, typed state, defined transitions, and deterministic control over irreversible actions.

1.1 Anatomy of an Agent

Every agent in a production system has five components. Designing each explicitly prevents the most common failure modes.

ComponentWhat it isProduction requirement
System prompt The agent's role, scope, output format, and constraints. Version-controlled in Git; pinned at deployment; includes explicit scope limits (what the agent must NOT do).
Tools Typed functions the agent can call: search, DB read/write, API call, code execution. Least-privilege — read tools and write tools are separate objects. Each tool has a JSON schema the framework validates before execution.
Memory In-context state, external vector/graph store, or episodic log. Three layers: in-context (current task), semantic (vector DB for retrieval), episodic (structured log via Zep or Mem0).
Control flow The logic that decides when the agent stops, loops, or hands off. Explicit exit conditions; max-iteration guards; typed output schemas so downstream nodes parse reliably.
Observability Traces, metrics, and logs emitted by the agent at runtime. OpenTelemetry spans per tool call; cost and latency captured per node; trace IDs propagated across agent handoffs.

2.1 Planner — Template

The Planner is the only agent with full access to the user query. It emits a machine-readable plan — not prose — so all downstream agents parse it deterministically.

System Prompt Template

# PLANNER SYSTEM PROMPT
You are a research planning agent. Your only job is to decompose
the user request into a JSON task DAG. Do NOT perform research.

Output schema (TypeScript):
interface Plan {
  goal: "string";                  // restated goal, one sentence
  tasks: Task[];
  hitl_checkpoints: "task_id"[]; // tasks requiring human approval
  success_criteria: "string"[];   // measurable exit conditions
  abort_conditions: "string"[];   // conditions triggering stop
}

interface Task {
  id: "string";         // e.g. "T1", "T2"
  role: "retriever" | "critic" | "writer" | "human";
  description: "string";
  depends_on: "task_id"[];
  parallel: boolean;   // can run alongside sibling tasks?
  tools: "string"[];    // from approved tool registry
  max_retries: number;  // loop guard
}

Rules:
- Favor small tasks with a single clear output.
- Mark parallel: true only when tasks have no data dependency.
- Never assign tools outside the approved registry below.
- Insert hitl_checkpoints before any external publish or write action.

Approved tool registry: web_search, kb_lookup, sql_read, graph_query,
code_run_sandbox, draft_email (read-only tools only at Retriever stage).

2.2 Retriever — Template

The Retriever's output quality is the single biggest lever on the final answer. Measuring retrieval separately from generation — recall and faithfulness as distinct metrics — is the non-negotiable first step.

System Prompt Template

# RETRIEVER SYSTEM PROMPT
You are a retrieval specialist. Execute exactly the task assigned by
the Planner. Return evidence in the canonical citation format below.
Do NOT synthesize, interpret, or write conclusions.

Citation format (required for every snippet):
[SOURCE_ID · source_name · section/lines · retrieved_at · confidence:0-1]

Output schema:
interface RetrievalResult {
  task_id:    "string";
  snippets:   Snippet[];
  coverage:   "complete" | "partial" | "insufficient";
  gaps:       "string"[];  // topics with no evidence found
  corpus_ver: "string";   // version tag for reproducibility
}

interface Snippet {
  text:       "string";
  citation:   "string";  // canonical format above
  confidence: number;    // 0–1 retrieval score
  freshness:  "string";  // ISO date of document
}

Rules:
- If coverage is "insufficient", surface gaps immediately — do not invent.
- Tag documents older than 90 days as STALE in the citation.
- Use graph traversal (not similarity search) for named entities.

2.3 Critic — Template

The Critic is optimized for error detection, not fluency. It outputs a machine-parseable diagnostic that drives the orchestrator's feedback loop.

System Prompt Template

# CRITIC SYSTEM PROMPT
You are an adversarial reviewer. Examine the evidence artifacts below
and return a structured diagnostic. Do NOT rewrite or improve — only detect.

Output schema:
interface CriticReport {
  status:   "NO_GAPS" | "GAPS_FOUND" | "ABORT";
  issues:   Issue[];
  confidence_floor: number; // lowest confidence score across snippets
  retry_tasks: "task_id"[]; // tasks the Retriever must redo
  abort_reason?: "string";   // required if status === "ABORT"
}

interface Issue {
  type:        "missing_citation" | "contradiction" | "stale_source" |
               "policy_violation" | "coverage_gap" | "low_confidence";
  description: "string";
  severity:    "low" | "medium" | "high" | "critical";
  location:    "string"; // snippet ID or task reference
}

Rules:
- Set status ABORT if any issue is "critical" or confidence_floor < 0.4.
- Set status GAPS_FOUND if retry_tasks is non-empty.
- Set status NO_GAPS only when zero issues are detected.
- Maximum 3 GAPS_FOUND cycles before escalating to human review.

2.4 Writer — Template

The Writer receives only critic-approved evidence. Tool access is disabled — it cannot perform additional research. Unsupported claims are a schema validation error.

System Prompt Template

# WRITER SYSTEM PROMPT
You are an evidence-bound technical writer. You will receive a validated
evidence package and a target format. Write ONLY from the evidence provided.

Hard constraints:
- Every factual claim MUST reference a snippet citation by ID.
- If evidence is insufficient for a section, write: [INSUFFICIENT EVIDENCE — flag for human review]
- Do NOT use training knowledge. Evidence package is the only source.
- Tool access: NONE.

Output schema (varies by format — example: report):
interface Report {
  title:            "string";
  executive_summary: "string";  // ≤150 words
  sections:          Section[];
  citations:         Citation[];  // full citation list
  confidence_score:  number;       // avg of all snippet confidences used
  review_flags:      "string"[];  // list of sections needing human review
}

2.5 Shared State Schema

All agents read from and write to a single typed state object managed by the orchestrator. This prevents implicit coupling and makes every transition auditable.

# Shared State — TypeScript interface (maps to LangGraph StateGraph annotations)
interface ResearchState {
  // Core identifiers
  run_id:         "string";          // UUID; propagated as OTel trace ID
  user_query:     "string";
  plan:           Plan | null;

  // Retrieval
  evidence:       RetrievalResult[];
  retrieval_iter: number;           // incremented each Retriever call

  // Critique
  critic_report:  CriticReport | null;
  critic_loops:   number;           // guard against infinite loops

  // Output
  draft:          Report | null;
  final_output:   Report | null;

  // Control
  hitl_pending:   boolean;
  hitl_decision:  "approved" | "rejected" | null;
  status:         "planning" | "retrieving" | "critiquing" | "writing" |
                  "hitl_wait" | "complete" | "aborted";
  error:          "string | null";
}

3. Orchestration Pattern Templates

The same four agents produce entirely different systems depending on how they are wired together. Each pattern below is a self-contained design: it includes the flow diagram (showing all paths — happy, error, and guard), three concrete business use cases, and implementation snippets across LangGraph, n8n, Langflow, and AWS.

Pattern selection rule. Choose the simplest pattern whose diagram matches your failure modes — not the most sophisticated one. Complexity compounds: a Hierarchical Tree with feedback loops inside each branch is hard to debug at 2 AM. Add one layer of complexity at a time, validate with eval, then add the next.

3.1 Sequential Pipeline

The linear chain is the simplest and most auditable pattern. Every node has exactly one predecessor and one successor. The audit trail is a straight line: trivially reconstructable, trivially testable.

Full Flow Diagram

INPUT ─────────────────────────────────────────────────────────────── OUTPUT [ USER QUERY ] │ ▼ [ PLANNER ] ──── emits: Plan JSON (task list, success criteria, abort conditions) │ │ on schema validation error ──▶ [ ERROR NODE ] ──▶ return 400 ▼ [ RETRIEVER ] ── fetches evidence from KB / web / SQL │ │ on tool failure ──▶ retry ×2 ──▶ [ ERROR NODE ] ──▶ surface gap ▼ [ CRITIC ] ────── validates evidence; outputs CriticReport │ │ ⚠ In pure sequential mode, Critic does NOT loop back. │ It annotates gaps into the report and passes forward. ▼ [ HITL GATE ] ── human reviews CriticReport + evidence summary │ │ approved ──────────────────────────────────────── rejected ──▶ [ ESCALATE ] │ ▼ [ WRITER ] ───── synthesises evidence-bound output │ ▼ [ OUTPUT ] ───── delivered + logged to audit store Key invariant: every node emits exactly one typed output. No implicit side effects. No shared mutable state. Audit: one DynamoDB / CloudWatch log entry per node transition. Replay = re-run from checkpoint.

3.2 Concurrent Fan-Out

Fan-out dispatches independent sub-tasks to parallel workers, then merges results before proceeding. Wall-clock latency equals the slowest worker, not the sum of all. The Aggregator node is the critical piece: it must deduplicate, rerank, and normalise citations across heterogeneous sources.

Full Flow Diagram

[ PLANNER ] ── emits parallel task list (T1, T2, T3 all parallel:true) │ │ route_to_retrievers() dispatches Send() per task │ ├──────────────────────────────────────────────────────────┐ │ │ │ ▼ ▼ ▼ [ RETRIEVER: web ] [ RETRIEVER: KB ] [ RETRIEVER: SQL ] Tavily search Bedrock KB / pgvector RDS read replica → 5 snippets → 8 snippets → 3 rows → snippets │ │ │ └──────────────────────────▶│◀─────────────────────────────┘ ▼ [ AGGREGATOR ] 1. Merge snippet lists 2. Deduplicate by source_id 3. Rerank by cross-encoder score 4. Keep top-K (default: 12) 5. Normalise citation format │ on aggregation error ──▶ [ ERROR ] ▼ [ CRITIC ] ── validates merged evidence │ NO_GAPS ────▶ [ HITL ] ──▶ [ WRITER ] ──▶ [ OUTPUT ] │ ABORT ────▶ [ ESCALATE ] Speed gain: 3 parallel retrievers at ~4s each = 4s total (vs. 12s sequential). Risk: workers make inconsistent assumptions. Aggregator MUST normalise before Critic sees results.

Best Use Cases

LangGraph — Fan-Out with Send API

from langgraph.types import Send
from typing import Annotated
import operator

# State must use an Annotated reducer to collect parallel results
class ResearchState(TypedDict):
    evidence: Annotated[list, operator.add]  # reducer: append, not replace
    # ... other fields

def route_to_retrievers(state: ResearchState) -> list:
    # Send() dispatches parallel instances of the retriever node
    return [
        Send("retriever", {
            "task":   task,
            "run_id": state["run_id"],
            "iter":   state["retrieval_iter"]
        })
        for task in state["plan"]["tasks"]
        if task["role"] == "retriever" and task["parallel"]
    ]

async def aggregator_node(state: ResearchState) -> dict:
    snippets = []
    seen_ids = set()
    for result in state["evidence"]:
        for s in result["snippets"]:
            if s["source_id"] not in seen_ids:
                snippets.append(s)
                seen_ids.add(s["source_id"])
    # Rerank by confidence score descending, keep top 12
    snippets.sort(key=lambda x: x["confidence"], reverse=True)
    return {"evidence": [snippets[:12]]}

graph.add_conditional_edges("planner",   route_to_retrievers, ["retriever"])
graph.add_edge("retriever",              "aggregator")
graph.add_edge("aggregator",             "critic")

3.3 Feedback Loop (Critic → Retriever Cycle)

The feedback loop gives the system self-correction capability: the Critic inspects evidence, identifies gaps, and re-tasks the Retriever with refined queries until quality thresholds pass. The hard max-loop guard is not optional — without it, a poorly scoped query can recurse indefinitely.

Full Flow Diagram

[ PLANNER ] ── emits initial task list + success_criteria + abort_conditions │ ▼ [ RETRIEVER ] ◀────────────────────────────────────────┐ │ state.retrieval_iter += 1 │ │ on iter 1: use original queries from Plan │ GAPS_FOUND: │ on iter 2+: use critic_report.retry_queries │ re-run with ▼ │ refined queries [ CRITIC ] │ │ │ ├── status == NO_GAPS ────────────────────────────▶ exit loop │ │ ├── status == GAPS_FOUND AND loops < 3 ──────────┘ │ • increment critic_loops │ • inject retry_queries into state │ • clear stale evidence list │ ├── status == GAPS_FOUND AND loops ≥ 3 ──────────▶ [ ESCALATE ] │ (loop guard triggered — do not loop again) │ └── status == ABORT ──────────────────────────────▶ [ ESCALATE ] (critical issue or confidence_floor < 0.4) After exit loop: │ ▼ [ HITL GATE ] ── human sees evidence + CriticReport │ approved ──▶ [ WRITER ] ──▶ [ OUTPUT ] rejected ──▶ [ ESCALATE ] Loop cost: each cycle ≈ $0.02–0.08 at Haiku rates. Budget ceiling in state prevents runaway. Trace: LangSmith records each loop as a separate span — you can replay loop N to debug.

3.4 Hierarchical Tree (Supervisor → Worker Squads)

For large tasks spanning multiple domains, a Supervisor decomposes the problem into domain squads, each of which runs the full 4-agent pipeline independently. A Synthesis Writer at the top merges their outputs. Never pass full text upward — only citation IDs; the Synthesis Writer fetches full snippets from a shared evidence store.

3.5 Orchestrator-Worker (Dynamic Task Dispatch)

An Orchestrator agent maintains a task queue and dynamically selects and dispatches to specialist Worker agents based on the current state. Unlike the Hierarchical Tree where squads are predetermined, the Orchestrator can choose which worker to invoke next based on intermediate results. This pattern enables true dynamic routing — but makes it harder to trace and debug than static graphs.

Full Flow Diagram

[ USER REQUEST ] │ ▼ [ ORCHESTRATOR ] ← stateful; sees all previous results • Maintains task queue • Selects next worker based on current state • Re-evaluates queue after each worker completes • Terminates when all tasks done OR abort condition met │ │ select_next_worker(state) → worker_type │ ├──────────────────────────────────────────────────────┐ │ │ ┌─▼──────────────┐ ┌─────────────────┐ ┌──────────▼──────┐ │ WORKER: Search │ │ WORKER: Analyst │ │ WORKER: Drafter │ │ (retriever) │ │ (critic/QA) │ │ (writer) │ │ tools: web, KB │ │ tools: none │ │ tools: none │ └────────────────┘ └─────────────────┘ └─────────────────┘ │ │ │ └──────────────────────────▼───────────────────────┘ results written to shared state │ Orchestrator re-evaluates: • task_queue empty → done • new tasks revealed by results → continue • abort condition met → escalate Key difference from Hierarchical: Orchestrator can invoke Worker A → Worker B → Worker A again. The path is not predetermined. Risk: Orchestrator context window grows with every iteration. Use state summarisation node.

3.6 Blackboard / Mesh

In the Blackboard pattern, agents do not call each other directly — they read from and write to a shared structured event store (the "blackboard"). Each agent watches for relevant state changes and reacts. This enables emergent coordination but sacrifices determinism. Use only for exploratory, non-compliance-critical workflows.

Full Flow Diagram

── Traditional (sequential/tree): agents call each other ────────────────────── A ──▶ B ──▶ C (predetermined path) ── Blackboard: agents publish/subscribe to shared store ─────────────────────── ┌─────────────────────────────────┐ │ BLACKBOARD (event store) │ │ events: [ │ │ {type:"query_posted", ...} │ │ {type:"evidence_added", ...} │ │ {type:"gap_found", ...} │ │ {type:"draft_ready", ...} │ │ ] │ └──────┬──────────────────────────┘ │ subscribe / publish ┌────────────┼─────────────┬──────────────┐ │ │ │ │ ▼ ▼ ▼ ▼ [ PLANNER ] [ RETRIEVER] [ CRITIC ] [ WRITER ] watches: watches: watches: watches: query_posted task_assigned evidence_added draft_requested publishes: publishes: publishes: publishes: tasks[] evidence[] gap_found[] draft_ready Each agent is autonomous: it wakes when its trigger condition is met, acts, and publishes results. Multiple agents can act simultaneously if their triggers fire at the same time. Risk: non-deterministic execution order. Never use for compliance, financial, or regulated outputs. Guard: max event count, TTL per run, mandatory HITL before any external action.

Best Use Cases

#Use caseWhy Blackboard fitsAvoid if…

Signal volume varies. Multiple agents (trend spotter, sentiment scorer, alert drafter) can react to the same event independently. Emergent alerting patterns are acceptable. The output triggers financial trades or regulatory filings — use sequential + HITL instead

A chemistry agent's finding might trigger a biology agent to re-examine its hypothesis. The goal is breadth of ideas, not a single deterministic output. from langgraph.graph import StateGraph, END
from typing import Annotated
import operator

class BlackboardState(TypedDict):
    events:     Annotated[list, operator.add]   # append-only event log
    tasks:      Annotated[list, operator.add]
    evidence:   Annotated[list, operator.add]
    gaps:       Annotated[list, operator.add]
    drafts:     Annotated[list, operator.add]
    iteration:  int
    status:     str

def route_blackboard(state: BlackboardState) -> str:
    # Router inspects latest event to decide next active agent
    last_event = state["events"][-1]["type"] if state["events"] else "start"
    if state["iteration"] > 20: return "escalate"   # hard event count guard
    if last_event == "query_posted":    return "planner"
    if last_event == "tasks_published": return "retriever"
    if last_event == "evidence_added":  return "critic"
    if last_event == "gap_found":       return "retriever"
    if last_event == "no_gaps":         return "hitl"
    return "escalate"

g = StateGraph(BlackboardState)
g.add_node("planner",    planner_node)
g.add_node("retriever",  retriever_node)
g.add_node("critic",     critic_node)
g.add_node("hitl",       hitl_node)
g.add_node("escalate",   escalation_node)

g.set_entry_point("planner")
# All nodes return to the router — router decides who acts next
for node in ["planner", "retriever", "critic"]:
    g.add_conditional_edges(node, route_blackboard,
        {"planner":"planner", "retriever":"retriever", "critic":"critic",
         "hitl":"hitl", "escalate":"escalate"})

Use the blackboard pattern only in internal-facing exploratory systems, never on externally-published outputs.

5.3 Architecture Quality Checklist

Embed this into your CI pipeline or architecture review template. Every item maps to a known failure mode.

  • State schema is typed and versioned. All agents read/write a single typed state object. Schema is committed to Git alongside the graph.
  • Every tool has a JSON schema. The orchestrator validates tool inputs against the schema before execution. Invalid inputs raise a typed error, not a runtime exception.
  • Read and write tools are separate objects. Retriever agents cannot access write tools. Write tools require explicit approval node preceding them.
  • Feedback loops have hard max-iteration guards. Critic → Retriever loops abort at N iterations (default: 3) and escalate rather than looping forever.
  • HITL gates are hardcoded, not optional. interrupt_before / waitForTaskToken / Wait nodes are in the graph definition, not in the prompt.
  • Prompts are version-controlled and pinned at deploy. LangSmith Hub pull with explicit version tag, or Git SHA reference. No "latest" in production.
  • State checkpoints persist to durable storage. PostgresSaver / DynamoDB / Redis — not in-memory. Long-running runs survive Lambda timeouts and restarts.
  • Eval dataset exists before go-live. Minimum 50 graded scenarios from real or representative inputs, including adversarial cases. Release gate ≥ 85% task completion.
  • Observability records emitted per run. LangSmith trace + CloudWatch metric per run. Escalation rate, cost-per-run, and critic_loops on a live dashboard.
  • Canary deploy with rollback trigger defined. 5% traffic first; pre-committed rollback if task-completion drops below threshold or cost-per-run exceeds ceiling.
  • Model provider failover configured. Priority-ordered fallback: Anthropic → OpenAI → open-weight via Bedrock. Tested and eval-validated before production.
  • Audit trail captures reasoning, not just outputs. Every Critic decision logs the issue list. Every Writer output logs the snippet IDs used. Retained ≥ 90 days.
